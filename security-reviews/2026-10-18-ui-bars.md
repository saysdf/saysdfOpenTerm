# Security review: UI bars (menu bar, startup banner, hotkey status bar)

Date: 2026-10-18. Commits: 9fb826db0, aa318f552, 99ade5456. Mode: read-only access to the sources; nothing was built or run.

Scope: `wezterm-gui/src/termwindow/saysdf_bars.rs`, `saysdf_menu.rs`; upstream patch points (`render/borders.rs`, `render/paint.rs`, `mod.rs`, `mouseevent.rs`, `keyevent.rs`, `scripting/guiwin.rs`); Lua `saysdf/lua/saysdf/{menu,hotbar,help,palette,util,status}.lua`; the design.md of the three changes; `saysdf/cli/src/cmd/help.rs`.

## Verdict: OK WITH CAVEATS

The main property of the threat model holds: bar data reaches Rust only from the Lua config (`window:saysdf_set_bar`), and terminal output has no path to either the item text or the action `id`s. Actions are executed only via `saysdf-bar-action(id)` → `saysdf.palette.run` → a lookup in the trusted registry → `window:perform_action(entry.action)`; an unknown `id` produces a log warning. The built-in help and the banner are embedded at build time, with no external requests. One medium-severity hit-testing bug was found (a click on "…" in the status bar runs an invisible action) and several low/informational remarks.

## Findings

### M1 (Medium). A click on "…" in the bottom bar runs a hidden hint

- `wezterm-gui/src/termwindow/saysdf_bars.rs:1010-1011` — the overflow element `…` gets `idx = fit.overflow` (the index of the first hidden left element) and the same `UIItemType::SaysdfBar{bar, Left, idx}` as ordinary items.
- `saysdf_bars.rs:855-881` (`saysdf_bar_mouse`): the first two branches (open the menu) apply only to `BarKind::Top`; for `BarKind::Bottom` the third branch `else if let Some(id) = item.id { saysdf_emit_bar_action(id) }` fires — i.e. a click on the visible "…" runs the action of the **first hidden** hint (for example `git.commit`, `core.copy`), which the user cannot see. Overflow in the status bar is realistic: up to 6 hints plus the right part (git/monitor) in a narrow window.
- For the top bar the behavior is correct (the nearest menu opens).

Fix: mark the overflow element explicitly — for example `idx: usize::MAX` or a separate `BarSide::Overflow`, and in `saysdf_bar_mouse` do nothing for `Bottom` + overflow (or open the palette/InputSelector with the hidden hints); for `Top` + overflow keep the current behavior, `saysdf_open_menu_at_title`. Add a unit test for `fit_items` + hit.

### L1 (Low). The click index comes from a stale frame: the action may differ from the one shown

- `SaysdfBarHit` stores only `idx` (`saysdf_bars.rs:66-70`); `ui_items` are rebuilt only on paint (`render/paint.rs:173`), while the specification is updated immediately in `saysdf_set_bar` (`saysdf_bars.rs:587-620`, via `TermWindowNotif::Apply`). A click arriving between applying a new specification and the next frame is resolved against the new list → the item at the same index in the new list is executed.
- For the status bar the list changes when the context changes (`hotbar.lua:31-51`): selection, alt-screen, the user vars `SAYSDF_TOOL`/`SAYSDF_DB_MODE` — a program in the pane can switch the latter arbitrarily, so the moment of the change is partly controlled from outside. All possible actions come from the trusted registry, so the risk is low.
- The menu (`saysdf_menu.rs`) is not affected: the model is a snapshot taken at open time, and row `idx` values are absolute.

Fix: add a `version: u64` field to `SaysdfBarHit` (the value of `BarsState.version` at `bar_element` time) and in `saysdf_bar_mouse` ignore a click when `hit.version != self.saysdf_bars.version`. Alternative — store the `id` itself in the hit (then `UIItemType` stops being `Copy`).

### L2 (Low). `sanitize_text` does not filter bidi/zero-width characters

- `saysdf_bars.rs:120-125`: only `char::is_control()` (category Cc) is replaced. U+200B–U+200F, U+202A–U+202E, U+2066–U+2069, U+FEFF, U+00AD, U+2028/2029 and combining marks pass through.
- The only semi-trusted text that reaches the bars is the right part of the status bar: the git branch name/label from the repository in the pane's cwd (`git.lua:315-333`, `format_status` `git.lua:118-146`; the cwd is set by the program via OSC 7, but `root_of` works only for the local domain, and the user would need a hostile repository). The right element has no `id` (`hotbar.lua:142-145`), a click on it does nothing, so the consequences are purely visual spoofing of a hint. With `bidi_enabled` off (the default) there is no reordering; zero-width characters have width 0 both in `fit_items` and when drawing — consistently.

Fix: in `sanitize_text` additionally replace with a space the category-Cf characters from the ranges listed (an explicit list is enough, no external crates) and U+2028/U+2029.

### I1 (Info). User vars switch the hint context; the "⚠ DB: WRITE ENABLED" warning is not a trust boundary

- `hotbar.lua:97-105` reads `SAYSDF_DB_MODE`/`SAYSDF_TOOL` from `pane:get_user_vars()`; `context()` uses them only as flags (`hotbar.lua:33-38`), and the hint text is the static `M.STATIC` and the registry (`hotbar.lua:54-57, 61-94`). There is no text or `id` injection — consistent with the design (design of change `hotkey-statusbar`).
- Consequence: any program in the pane (including a remote one over SSH, OSC 1337 passes through the pty) can show a false write-mode warning or, conversely, hide a genuine one if it writes to the same pty in parallel with `saysdf db` (a background process). This is a UX hint, not protection; the actual mode is controlled by `saysdf db` itself (`saysdf/cli/src/db/ui.rs:442, 1908-1919`).

Possible hardening (optional): for the local domain take `db_danger` into account only when `process_basename(info.process) == "saysdf"`, and for an SSH domain show it neutrally (for example "DB: write (remote)"). State in help.md that the hint is informational.

### I2 (Info). F1/F9 interception and input into an open menu

- F1/F9 are ordinary `config.keys` with an `action_callback` (`menu.lua:334-351`, `help.lua:129-142`); with a TUI in the foreground (`util.lua:193-208`: alt-screen or a process name from the list) the key is forwarded to the program via `SendKey`. For SSH/multiplexer the process name is unknown → only alt-screen decides; this is documented. A program can only *take* F1/F9 for itself (alt-screen), but cannot make the terminal swallow other keys.
- Passwords: while the menu is open, all keys are absorbed by the modal (`saysdf_menu.rs:586-598`); nothing goes to the program or the logs. Side effect: an accidentally opened menu + continued typing → letters act as accelerators (File menu: the Exit and New Window items have letter accelerators). No leak; the way out is Esc/F9.
- Banner: `saysdf_key_down` (`saysdf_bars.rs:885-898`, `keyevent.rs:272-275`) hides the banner on any non-modifier key and passes the key on; only one Esc is swallowed. Acceptable.

### I3 (Info). Dispatch of `saysdf-bar-action`

- `saysdf_bars.rs:901-920` → `config::lua::emit_event` (`config/src/lua.rs:769-794`): all handlers are called in registration order; a handler that returns `false` stops the rest. If the user config registers its own `wezterm.on("saysdf-bar-action")` before `palette.ensure_bar_action()` and returns `false`, the bar actions silently stop working. This is upstream semantics; it can be mentioned in the module documentation.
- `palette.run` (`palette.lua:125-133`): `by_id` re-evaluates the registry sources at click time; an unknown `id` → `log_warn`, an error → `pcall` + `log_error` (`palette.lua:144-149`). Re-entrancy: the menu is closed before the emit (`saysdf_menu.rs:392-396`), the event is asynchronous; multiple clicks give a queue of `perform_action`s, with no shared mutable state in Rust.

### I4 (Info). Parsing of Lua data and layout arithmetic are fine

- Limits: 64 elements per side, 64 children, 1 nesting level, 256 characters of text (`saysdf_bars.rs:38-47, 142-210`); banner ≤ 5 lines, timeout ≤ 600 s (`saysdf_bars.rs:606-611`), NaN/negative → 0. Non-string fields are a Lua error, not a panic. Invalid UTF-8 → a `to_str` error.
- Layout: `layout_rows`/`bar_ys` use `saturating_sub`, `fit_items` never goes negative (`right_used ≤ width` by construction), `truncate_cells` is protected against `max == 0`, division by `cell_h.max(1)`. In `MenuModel` the indices `menus[current]`/`% n` are correct because menus are filtered by non-empty `children`; in `scroll_view`, `total > avail` guarantees `total - cap ≥ 0`. `unwrap()` only on `render_state` (as in upstream at the same paint site). Palette indices `[3,4,6,2]`/`+8` are within the arrays.

### I5 (Info). Help/banner content

- `saysdf/cli/src/cmd/help.rs:6-7` — `include_str!` for `help.md` and `keymap.md`, shown in the built-in Markdown viewer; `help.md` has no URLs/downloads, and `md.rs` opens only local files via links. The banner lines are assembled from the registry (`help.lua:40-69`). No external requests.

## What was not checked

- The build, run, tests and screenshots were not done; conclusions come from reading the code only.
- The content of the dynamic registry sources `palette_entries()` in `ssh.lua`, `notify.lua`, `tabs.lua` (labels from the user's ssh config, etc.) was not audited; they are assumed to be trusted config.
- Rendering of combining/zero-width characters in the box model/shaper (overlap onto neighboring cells) was not traced.
- Platform behavior of `request_drag_move()` and of double-clicking an empty spot of the menu bar (`saysdf_bars.rs:1031-1037` → `mouseevent.rs:507-529`) — from upstream code only.
- The `util.hash` hash (FNV+djb2, non-cryptographic) used to skip updates: a collision merely means a stale bar; not analyzed specifically.
- Changes in the same commits outside the bars (`close.lua`, `workspaces.lua`, `screenshot.ps1`, the `saysdf db` CLI) — out of scope.

## Fixed

Date: 2026-10-18 (not committed at the time of writing).

- **M1** — `wezterm-gui/src/termwindow/saysdf_bars.rs`: the "…" element is marked with a separate kind `BarSide::Overflow` (in `bar_element`). The click decision is moved into the pure function `bar_click` → `BarClick`: for `Bottom` + overflow — `ShowAll` (the command palette opens with the full list, no hidden hint is executed); for `Top` + overflow — open the nearest hidden menu as before (`title_x` and switching titles in an open menu account for `Overflow`). Test `saysdf_click_bottom_overflow_runs_nothing_hidden`.
- **L1** — same place: `SaysdfBarHit.version` (the value of `BarsState.version` when the element was built; for the banner and menu rows it is 0, they do not use the version); `bar_click` returns `None` when `hit.version != self.saysdf_bars.version`. Test `saysdf_click_stale_version_ignored`. In `saysdf_menu.rs` — only the new field in a literal.
- **L2** — same place: `sanitize_text` additionally replaces with a space U+00AD, U+061C, U+180E, U+200B–U+200F, U+2028–U+202E, U+2060–U+2064, U+2066–U+2069, U+FEFF (`is_invisible_format`). Test `saysdf_sanitize_invisible_and_bidi`.
- **I1** — `saysdf/lua/saysdf/hotbar.lua`: `M.local_saysdf(info)`; the user vars `SAYSDF_DB_MODE`/`SAYSDF_TOOL` affect the context (`db_danger`, `tool`) only if the foreground process is `saysdf`/`saysdf.exe` in the `local` domain (an unknown domain is treated as local, as in `git.lua`). A program over SSH or a background process can no longer show or hide the warning. Test `hotbar_user_vars_only_from_local_saysdf` (and `hotbar_context_priority` was updated) in `saysdf/lua-bundle/src/ui_bars_tests.rs`.
- **I3** — the headers of `saysdf/lua/saysdf/palette.lua` and `menu.lua`: a custom `saysdf-bar-action` handler registered earlier that returns `false` will disable the bar actions.
- I2, I4, I5 — unchanged (nothing to fix).
